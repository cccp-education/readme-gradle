== Vision

readme-gradle consomme codebase (N1) comme socle LLM unifié et
implémente l'auto-traduction i18n selon le pattern bakery (EPIC
BKY-I18N) — le borough se traduit lui-même. Le plugin génère
automatiquement les 20 fichiers README (10 langues × 2 audiences :
consommateur + plugin) depuis un master EN unique via la tâche
`translateReadme`, en consommant `LlmBuildService` de codebase (N1)
et `i18n-contracts` (N0 MEMPHIS).

L'EPIC RM-12 (cadrage infra LLM) et RM-4b (use case i18n) sont cadrés
ensemble : l'infra est définie *pour* le use case, pas pour elle-même.

== Le pattern bakery (template de référence)

```
N0  i18n-contracts (MEMPHIS)
    ├── TranslationService      (interface)
    ├── TranslationRequest      (data class)
    ├── TranslationResult       (sealed Success/Failure)
    └── LanguageCatalog         (10 langues + RTL flag)

N2  bakery.llm.LlmService                   (port fun interface, coroutine)
    ↓ bridé par
N2  LlmServiceTranslationAdapter           (implémente TranslationService N0)
    ↓ consommé par
N2  LlmTranslationApplier                  (traduit FR→EN valeur par valeur, fallback)
    ↓ invoqué par
N2  MigrateToI18nTask / MigrateContentI18nTask  (tâches Gradle)

N2  RtlDirectionInjector                    (consomme LanguageCatalog N0)
N2  PostMigrationSnapshot                   (checksums delta)
N2  ValidationReport                        (audit cohérence)
```

Le pattern post-SLD-8 (slider SLD-5, capsule CAP-29) remplace
l'`OllamaLlmService` local par consommation `LlmBuildService` de
codebase N1 :

```
N2  {name}.llm.LlmService                   (port fun interface, coroutine)
    ↓ bridé par
N2  ChatModelLlmAdapter                     (bridge ChatModel langchain4j)
    ↓ obtenu via
N1  LlmBuildService + LlmProviderChatModelAdapter  (codebase N1)
```

== Transposition à readme-gradle (pattern post-SLD-8)

```
N0  i18n-contracts (MEMPHIS) — déjà publié
    ├── TranslationService
    ├── TranslationRequest / TranslationResult
    └── LanguageCatalog (10 langues + RTL)

N2  readme.llm.LlmService                   (port fun interface, coroutine)
    ↓ bridé par
N2  readme.llm.ChatModelLlmAdapter          (bridge ChatModel langchain4j)
    ↓ obtenu via
N1  LlmBuildService + LlmProviderChatModelAdapter  (codebase N1)

N2  readme.i18n.ReadmeTranslationServiceAdapter  (implémente TranslationService N0)
    ↓ consommé par
N2  readme.i18n.ReadmeTranslationApplier    (traduit README.md master → 10 langues)
    ↓ invoqué par
N2  TranslateReadmeTask                     (tâche Gradle translateReadme)

N2  readme.i18n.RtlDirectionHandler          (consomme LanguageCatalog N0, AR/UR)
N2  readme.i18n.ReadmeSnapshot               (checksums delta — régénération sync)
N2  readme.i18n.ReadmeValidationAuditor     (badges/switcher/marqueurs cohérents)
```

== Audit — 8 constats

| # | Constat | Preuve

| 1

| `readme-plugin/src/main/kotlin/readme/` — 9 fichiers, zéro import langchain4j, zéro `LlmBuildService`, zéro `CompositeContext`. Le bundle `readme.ai` (langchain4j-ollama, open-ai, gemini, mistral, pgvector, all-minilm) est en `compileOnly` (`build.gradle.kts:43`) mais aucune classe ne le consomme.

| 2
| `alias(libs.plugins.codebase)` appliqué mais codebase n'est pas consommé
| `build.gradle.kts:19` — le plugin codebase est appliqué mais le code source ne référence aucun service de codebase (`LlmBuildService`, `LlmProvider`, `LlmProviderChatModelAdapter`). Le plugin codebase est un no-op pour readme-gradle actuellement.

| 3
| Le bundle `readme.ai` compileOnly est du code mort
| `build.gradle.kts:43` — `compileOnly(libs.bundles.readme.ai)` déclare 6 modules langchain4j (ollama, open-ai, gemini, mistral, pgvector, all-minilm). Aucune classe production ne les importe. Si on consomme codebase N1 pour le LLM, c'est codebase qui fournit le bridge langchain4j — le bundle est caduc.

| 4
| `node-gradle` (RM-7) est aussi du code mort
| `build.gradle.kts:47` — `implementation(libs.node.gradle)` avec commentaire `//TODO: readme to html and serve`. Aucune classe ne consomme `gradle-node-plugin`. Dépendance inutilisée.

| 5
| Le README consommateur et le README plugin se chevauchent
| `README.md` racine (168 lignes) contient sections "Build & test" (`./gradlew -p readme-plugin build`) + matrice de tests — relèvent du dev plugin. `readme-plugin/README.md` (205 lignes) contient le module layout complet du dépôt. La frontière audience n'est pas nette.

| 6
| Les 20 fichiers i18n (10 langues × 2 audiences) ont été générés manuellement (session 007)
| `README.consommateurs/` (10 fichiers) + `README.plugin/` (10 fichiers) — générés à la main en session 007. Pas de régénération automatique. Si le master change, les 20 fichiers deviennent désynchronisés. RM-4b documenté "Automatisation dogfooding À FAIRE" dans le BACKLOG.

| 7
| Bakery a un pattern i18n mature et testé (EPIC BKY-I18N terminé)
| `bakery-plugin/.../i18n/` — 14 fichiers : LlmTranslationApplier, LlmServiceTranslationAdapter, I18nMigrationService, MigrateToI18nTask, MigrateContentI18nTask, RtlDirectionInjector, PostMigrationSnapshot, ValidationReport. Pattern complet avec checksums delta, dry-run, validation. C'est le template de référence.

== Décisions architecturales

. *Portée EPIC* : RM-12 définit l'infra LLM (`readme.llm` port +
  adapter + consommation codebase N1), RM-4b implémente le use case
  i18n (`readme.i18n` domaine + tâche `translateReadme` + 20 fichiers
  générés). Les deux EPICs sont cadrés ensemble — l'infra est définie
  *pour* le use case.

. *Pattern post-SLD-8* : consommation `LlmBuildService` de codebase N1
  (pattern slider SLD-5, capsule CAP-29), pas pattern legacy bakery
  (`OllamaLlmService` local). L'adapter `LlmProviderChatModelAdapter`
  est désormais consolidé côté codebase N1 (EPIC LLM-ADAPTER-EXTRACT
  S-073 terminé). readme-gradle consomme l'adapter N1, ne le duplique
  pas.

. *Domaine `readme.llm`* (nouveau, 1er) : port `LlmService` (fun
  interface, coroutine `suspend fun complete(prompt): String`) mirror
  `bakery.llm.LlmService` + `ChatModelLlmAdapter` (bridge ChatModel
  langchain4j via `LlmBuildService` N1). Pattern `slider.ai` post-SLD-8.

. *Domaine `readme.i18n`* (nouveau, 2ème) : mirror `bakery.i18n` —
  `ReadmeTranslationServiceAdapter` (implémente `TranslationService`
  N0), `ReadmeTranslationApplier` (traduit master → langues cibles),
  `TranslateReadmeTask` (tâche Gradle `translateReadme`),
  `RtlDirectionHandler` (consomme `LanguageCatalog` N0),
  `ReadmeSnapshot` + `ReadmeSnapshotLoader` (checksums delta),
  `ReadmeValidationAuditor` (badges/switcher/marqueurs cohérents).

. *Contexte augmenté* : pas de RAG pgvector. Le contenu à traduire
  est un README court et auto-contenu. Le prompt embarque le README.md
  master + règles de cohérence (badges, switcher i18n, marqueur
  `<!-- translated from README.md rev X -->`) + règles RTL pour AR/UR
  (pattern `RtlDirectionInjector` bakery). Pattern `DocKnowledgeBase`
  bakery avoidé — pas de contexte documentaire externe nécessaire.

. *2 README masters, 20 fichiers générés* : `README.md` racine
  (master consommateur EN) → `README.consommateurs/README.{lang}.md`
  × 9 + `readme-plugin/README.md` (master plugin EN) →
  `readme-plugin/README.plugin/README.{lang}.md` × 9. Chaque fichier
  reçoit marqueur `<!-- translated from README.md rev 0.0.1 -->` +
  switcher i18n + badges alignés + RTL natif AR/UR.

. *Suppression bundle `readme.ai` compileOnly* (RM-7 étendu) : les 6
  modules langchain4j (ollama, open-ai, gemini, mistral, pgvector,
  all-minilm) sont caducs — codebase N1 fournit le bridge. Suppression
  aussi de `node-gradle` (inutilisée). Cleanup préalable au cadrage.

. *Dépendance Gradle* : `implementation(libs.codebase.plugin)` déjà
  présent (`build.gradle.kts:19` via `alias(libs.plugins.codebase)`).
  Ajout `implementation(libs.i18n.contracts)` (N0, MEM-3 0.0.2 déjà
  publié Central). Pas de bump BOM.

. *Backward compat* : la tâche `translateReadme` est *additive*. Les
  3 tâches existantes (`generateReadme`, `transformReadme`,
  `commitGeneratedReadme`) sont inchangées. `translateReadme` ne
  dépend pas du pipeline PlantUML — elle traduit du Markdown, pas de
  l'AsciiDoc. Le consommateur qui ne veut pas l'i18n n'est pas impacté.

. *Méthode* : baby-step DDD/TDD/BDD, 3 niveaux tests/US
  (unit → functional → cucumber), English only code/Gherkin.

. *Ordre* : US-0 (cadrage ✅) → US-1 (cleanup dépendances RM-7 étendu)
  → US-2 (refonte README selon article 0124 RM-11) → US-3 (infra LLM
  `readme.llm`) → US-4 (domaine `readme.i18n` + adapter) → US-5
  (tâche `translateReadme` + dogfooding 20 fichiers) → US-6 (Cucumber
  BDD).

== Risques et mitigations

[cols="2,3,3", options="header"]
|===
| Risque | Impact | Mitigation

| Poids transitif codebase-plugin (RAG + pgvector + koog)
| Build time readme-plugin augmente
| slider + capsule + planner payent déjà ce coût sans issue. codebase-plugin est un JAR publié, résolu depuis Maven Central (pas recompilé).

| `LlmProviderChatModelAdapter` déjà consolidé N1 (S-073)
| Duplication si on copie côté readme
| On consomme l'adapter N1 (`codebase.koog.llm.adapter.LlmProviderChatModelAdapter`), on ne le copie pas. Pattern post-SLD-8 strict.

| Traduction LLM non-déterministe
| Régénération produit des résultats différents
| Checksums delta (pattern `PostMigrationSnapshot` bakery) — si le master n'a pas changé, skip. `--rerun-tasks` pour forcer la re-traduction.

| Fallback LLM unavailable
| Tâche échoue ou traduit mal
| Pattern `LlmTranslationApplier` bakery : `TranslationResult.Failure` → conserve la valeur source (fallback, pas de crash). `ReadmeValidationAuditor` signale les traductions manquées.

| 20 fichiers i18n existants (session 007) écrasés
| Perte des traductions manuelles
| Backup préalable (`.agents/sessions/010-readme-i18n-backup/`). La première exécution `translateReadme` remplace les 20 fichiers manuels par 20 fichiers LLM. Le master EN reste la source de vérité.
|===
