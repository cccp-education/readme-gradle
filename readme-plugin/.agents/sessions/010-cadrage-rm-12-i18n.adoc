== Contexte

L'utilisateur a demandé un brainstorming sur le borough readme-gradle.
Après chargement du contexte (INDEX, BACKLOG, PROMPT_REPRISE,
SESSION_CHECKLIST, README consommateur, README plugin, article 0124
sur l'architecture « Plugin Indépendant + Racine Consommateur »),
l'utilisateur a affiné la vision :

1. *Séparation README consommateur vs plugin* selon l'article 0124 —
   le consommateur = aide au use case de clonage + personnalisation ;
   le plugin = description exhaustive (tâches, périmètre, CI/CD,
   lien Central, version).

2. *LLM et contexte augmenté via codebase* comme bakery et les autres
   boroughs — readme-gradle ne réinvente pas sa pile IA, il consomme
   codebase N1.

3. *i18n selon le pattern bakery* (EPIC BKY-I18N) — le borough se
   traduit lui-même via `translateReadme`, pattern post-SLD-8
   (consommation `LlmBuildService` de codebase N1).

== Audit — 8 constats

. *readme-gradle n'utilise aucun LLM ni contexte augmenté aujourd'hui*
  — `src/main/kotlin/readme/` 9 fichiers, zéro import langchain4j, zéro
  `LlmBuildService`, zéro `CompositeContext`. Bundle `readme.ai` en
  `compileOnly` mais aucune classe ne le consomme.
. *`alias(libs.plugins.codebase)` appliqué mais codebase non consommé*
  — `build.gradle.kts:19`, le plugin est un no-op pour readme-gradle.
. *Bundle `readme.ai` compileOnly est du code mort* — 6 modules
  langchain4j (ollama, open-ai, gemini, mistral, pgvector, all-minilm)
  caducs si on consomme codebase N1.
. *`node-gradle` (RM-7) est aussi du code mort* — `build.gradle.kts:47`
  avec commentaire `//TODO: readme to html and serve`, aucune classe
  ne consomme `gradle-node-plugin`.
. *README consommateur et README plugin se chevauchent* — README.md
  racine (168 lignes) contient sections dev. readme-plugin/README.md
  (205 lignes) contient le module layout complet. Frontière floue.
. *20 fichiers i18n générés manuellement (session 007)* — pas de
  régénération auto. Si le master change, les 20 fichiers désync.
. *Bakery a un pattern i18n mature (EPIC BKY-I18N terminé S-194)* —
  14 fichiers domaine `bakery.i18n` + `bakery.llm`. Template de
  référence.
. *Slider a le pattern post-SLD-8 pour la consommation codebase* —
  `AssistantManager.kt:76-113` `registerLlmBuildService()` +
  `resolveModel()`. SLD-5 (DeckTranslator + translateDeck) est le
  pattern le plus proche (traduction one-to-many).

== Décisions architecturales (11)

. *Portée EPIC* : RM-12 = infra LLM, RM-4b = use case i18n. Cadrés
  ensemble — l'infra est définie *pour* le use case.
. *Pattern post-SLD-8* : consommation `LlmBuildService` de codebase N1
  (slider SLD-5, capsule CAP-29), pas legacy bakery (`OllamaLlmService`).
. *Domaine `readme.llm`* (1er) : port `LlmService` fun interface +
  `ChatModelLlmAdapter` bridge ChatModel langchain4j via N1.
. *Domaine `readme.i18n`* (2ème) : mirror `bakery.i18n` —
  `ReadmeTranslationServiceAdapter`, `ReadmeTranslationApplier`,
  `TranslateReadmeTask`, `RtlDirectionHandler`, `ReadmeSnapshot`,
  `ReadmeValidationAuditor`.
. *Contexte augmenté* : pas de RAG pgvector. README court auto-contenu.
  Prompt embarque master + règles cohérence + règles RTL.
. *2 README masters, 20 fichiers générés* : `README.md` racine → 9
  traductions + `readme-plugin/README.md` → 9 traductions. Marqueur
  `<!-- translated from -->` + switcher + badges + RTL natif AR/UR.
. *Suppression bundle `readme.ai` compileOnly* (RM-7 étendu) + `node-gradle`.
. *Dépendance Gradle* : `i18n-contracts` 0.0.2 (N0) ajouté. Pas de bump BOM.
. *Backward compat* : `translateReadme` additive. 3 tâches existantes
  inchangées. `translateReadme` ne dépend pas du pipeline PlantUML.
. *Méthode* : baby-step DDD/TDD/BDD, 3 niveaux tests/US, English only.
. *Ordre* : US-1 (cleanup) → US-2 (refonte README) → US-3 (infra LLM)
  → US-4 (domaine i18n) → US-5 (tâche + dogfooding) → US-6 (Cucumber).
